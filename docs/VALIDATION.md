# 검증 기록 — 00–31장 완성본

확인일: **2026-11-09**. 이 기록은 [교재 전체 목차](../book/README.md)의 32장과 실행 코드·연습문제·해설을 통합한 결과입니다. 아래의 실행 기록은 해당 시점의 결과이며, 이후 변경의 상태는 [GitHub Actions](https://github.com/praster1/GoLang_all_in_one/actions)에서 확인합니다.

## 1. 확인한 환경과 범위

- 로컬 실행 환경: Linux amd64, **Go 1.27.3**, race detector에 필요한 C 컴파일러 사용.
- 모듈 기준: `go 1.27.0`. 현재 학습 계열은 Go 1.27이며 다른 계열을 검증 없이 지원한다고 가정하지 않습니다.
- 본문·문제·해설: 각각 **32장**. 장 번호 00–31의 학습 경로와 이전·다음 장 링크를 연결했습니다.
- 실제 `main.go` 프로그램 **346개**의 전체 코드가 해당 본문 또는 해설의 Go 코드 블록과 일치합니다.
- 예제·해설·문서 검사 도구의 Go 파일은 **843개**, 그중 테스트 파일은 **466개**입니다. 파일 수는 학습 완성도나 테스트 충분성의 대용 지표가 아닙니다.
- SQL 실습은 `modernc.org/sqlite v1.62.0`을 사용합니다. 의존성은 `go.mod`와 `go.sum`에 고정했으며 별도 DB 서버·계정 없이 실행했습니다.

00–04장의 기존 내용을 유지하고 05–31장을 집필했습니다. 04장의 다음 장 링크, 전체 목차와 예제·문제·해설 색인을 완료 범위에 맞게 갱신했습니다.

## 2. 전체 저장소 검사

아래 명령을 저장소 루트에서 실행했습니다. 모두 종료 코드 0으로 완료했습니다.

| 명령 | 확인한 결과 |
| --- | --- |
| `go fmt ./...` 및 `gofmt -l .` | 추가로 바뀌어야 할 포맷 없음 |
| `go vet ./...` | 정적 검사 통과 |
| `go build ./...` | 전체 패키지 빌드 통과 |
| `go test -count=1 ./...` | 캐시 결과를 사용하지 않고 365개 패키지 검사; 테스트가 있는 360개 패키지 통과 |
| `go test -race -count=1 ./...` | 전체 패키지 검사에서 데이터 레이스 보고 없음 |
| `go run ./tools/checkdocs` | 로컬 문서 파일 링크 검사 통과 |
| `go mod verify` | 내려받은 모듈의 체크섬 확인 통과 |
| `git diff --check` | 변경 내용의 공백 오류 없음 |

테스트가 없는 지원 패키지도 전체 빌드에 포함됩니다. `-race` 통과는 실행한 경로에서 레이스가 보고되지 않았다는 뜻이며, 실행하지 않은 모든 입력과 스케줄의 안전성을 증명하지는 않습니다.

재현 명령:

```sh
go version
go fmt ./...
go vet ./...
go build ./...
go test -count=1 ./...
go test -race -count=1 ./...
go run ./tools/checkdocs
go mod verify
```

## 3. 본문과 실행 안내

일반 빌드·테스트 외에 다음 학습 계약을 확인했습니다.

- **코드와 출력:** 장별 전체 코드 블록을 실제 소스와 대조하고, 예제의 실제 UTF-8 출력·오류·종료 코드를 문서와 비교했습니다. 입력·옵션이 필요한 CLI는 안내된 인자와 파이프 입력을 사용했습니다.
- **의도적인 실패:** 테스트 경계 오류, 잘못된 ResponseRecorder 재사용, 제네릭 제약 위반 등은 임시 파일에서 예상한 이유로 실패하는지 확인하고 수정 경로도 실행했습니다. 실패 파일은 정상 빌드 대상에 넣지 않았습니다.
- **패키지와 제네릭:** 여러 명령이 `internal` 패키지를 공유하는 경로와 `go list`·`go doc` 안내를 실행했습니다. Go 1.27의 자체 타입 매개변수가 있는 메서드는 실제 컴파일·실행했으며, 인터페이스의 제한과 구분했습니다.
- **개인 풀이 보존:** 제공하는 Bash 준비 블록을 임시 디렉터리에서 실행하고 재실행해 기존 풀이 파일이 덮어써지지 않는지 확인했습니다.
- **문서 검사 도구:** `first[int](nil)` 같은 인라인 코드를 링크로 잘못 인식하던 문제를 수정했습니다. 기존 검사와 함께 백틱 길이·줄바꿈·이스케이프·미완결 코드·실제 링크 유지에 관한 15개 회귀 사례를 검사합니다.
- **링크:** 로컬 파일 링크와 공식 웹 문서의 절 링크를 구분하여 점검했습니다. 점검 당시 본문·문제·해설에는 비어 있지 않은 로컬 `#fragment` 링크가 없었습니다.

공식 웹 링크 중 잘못된 `internal`·`testing` 절 링크를 수정했습니다. GNU Bash 문서 5개는 직접 HTTP 확인에서 서버 오류가 발생하여 공식 페이지의 검색 색인 내용으로 확인했습니다. 모든 외부 페이지가 언제나 접속된다는 보장은 하지 않습니다. PowerShell 준비 명령은 검토했지만 이 Linux 환경에서 실제 실행하지 않았습니다.

## 4. 세 가지 종합 실습

### 29장 — CSV 분석 CLI

입력 파일과 표준 입력, 헤더·필드·UTF-8·값·행 수·바이트 수 검증, 그룹별 집계, CSV·JSON, 종료 코드를 확인했습니다. 정확한 바이트 한도와 한 바이트 초과를 EOF·마지막 빈 줄·여러 바이트 문자 입력에서 구분합니다. 분석 실패 뒤에는 부분 보고서를 성공 출력으로 내보내지 않습니다.

병합 해설은 최대 10개 입력에 각각 기본 제한을 적용합니다. 100,000행에 각 1,000,000,000의 금액을 넣어 총합 100,000,000,000,000을 검증했습니다. 입력 실패 시 빈 Summary와 원인을 돌려주고, 같은 분류를 합친 뒤 이름순으로 정렬합니다.

```sh
go run ./examples/29-csv-cli/cmd/csvstats -input examples/29-csv-cli/testdata/sales.csv
go test ./examples/29-csv-cli/... ./solutions/29-csv-cli/...
```

추가로 `FuzzAnalyze`를 3초간 실행해 126,910회 입력을 검사했고 실패를 찾지 못했습니다. 이 횟수는 해당 실행 기록이며 다른 환경에서 같은 횟수가 나와야 하는 계약은 아닙니다.

### 30장 — 할 일 HTTP API

메모리와 SQLite 저장소에 동일한 저장소·HTTP 계약 테스트를 적용했습니다. 생성·조회·페이지 목록·수정·삭제, 동시 ID 발급, 요청 크기·UTF-8·필수 필드·오류 응답을 확인했습니다.

Linux의 실제 서버 실행 파일에서도 CRUD·HEAD·DELETE·404 응답을 확인했습니다. SIGTERM과 SIGINT로 정상 종료한 뒤 SQLite 파일로 서버를 다시 실행하여 기존 데이터가 남는지 확인했습니다. Windows amd64용 서버 교차 빌드도 통과했습니다.

```sh
go run ./examples/30-todo-api/http-demo
go test ./examples/30-todo-api/... ./solutions/30-todo-api/...
```

위 데모는 자동 종료합니다. 계속 실행하는 서버, SQLite 경로와 종료 방법은 [30장 본문](../book/30-todo-api/README.md)을 따릅니다.

### 31장 — 동시 배치 처리

고정 워커 수, 입력 순서의 결과 배열, 제한된 재시도, 영구 오류, 취소 후 워커 합류와 JSON 보고서를 검사했습니다. 취소는 협조적으로 처리하며 Processor가 Context를 무시하면 강제로 중단시킬 수 없습니다. 본문의 종료 계약과 테스트도 이 범위를 따릅니다.

```sh
go run ./examples/31-concurrent-batch/cmd/batch
go test ./examples/31-concurrent-batch/... ./solutions/31-concurrent-batch/...
```

`-timeout`은 입력을 읽은 뒤 배치 처리를 시작할 때 적용됩니다. 표준 입력을 기다리는 일반 Reader는 Context만으로 끊기지 않으므로 첫 Ctrl+C 이후 신호 가로채기를 해제하여 두 번째 Ctrl+C로 종료할 수 있게 했습니다. EOF를 전달해 정상적으로 읽기를 끝내는 방법도 본문에서 설명합니다.

Linux 실제 프로세스가 표준 입력의 `read(fd=0)`에서 기다리는 것을 확인한 뒤 두 번의 SIGINT로 종료하는 경로도 검사했습니다. 별도로 첫 SIGINT 뒤 EOF를 전달했을 때 취소 보고서와 종료 코드 130을 확인했습니다. 정상 0·항목 실패 1·사용법 오류 2·처리 시간 초과 130의 실제 프로세스 종료도 확인했습니다.

## 5. 성능·퍼징·배포

26장의 벤치마크 27개를 `-benchtime=1x -benchmem`으로 실행하여 벤치마크 경로가 작동하는지 확인했습니다. 1회 측정값으로 성능 우열을 결론내리지 않았습니다. Checksum 벤치마크에서는 별도로 CPU·메모리 프로파일을 생성하고 `pprof`의 CPU·할당 누적·유지 메모리 텍스트 보고서를 확인했습니다.

27장의 seed·회귀 사례는 전체 테스트에 포함합니다. 퍼징 실행 시간과 추가 입력 탐색 절차는 [27장](../book/27-fuzzing/README.md)에, 측정 조건과 해석은 [26장](../book/26-performance/README.md)에 있습니다.

28장의 실행 파일은 다음 대상으로 교차 빌드했습니다.

| 대상 | 로컬에서 확인한 범위 |
| --- | --- |
| Linux amd64 | 빌드, 정상 출력, 잘못된 입력의 종료 코드, 버전·리비전 주입, SHA-256 목록 |
| Windows amd64 | 실행 파일 생성; Windows에서의 실제 실행은 Actions 대상 |
| macOS arm64 | 실행 파일 생성; macOS에서의 실제 실행은 미확인 |
| Docker | 공식 기반 이미지 태그 확인; 이 로컬 환경에는 Docker가 없어 실제 빌드·실행은 Actions 대상 |

[일반 CI](../.github/workflows/ci.yml)는 Windows·Linux에서 전체 포맷·빌드·정적 검사·테스트·문서 링크를 검사하고 Linux에서 레이스 검사도 실행합니다. [산출물 CI](../.github/workflows/build-artifacts.yml)는 Linux·Windows 네이티브 실행 파일을 빌드·실행하고 체크섬 목록과 함께 보관하며, Docker 이미지를 빌드해 대표 출력을 확인합니다. 실제 CI 성공 여부는 해당 변경의 PR Checks와 Actions 실행 로그를 기준으로 확인합니다.

## 6. 검증 범위의 한계

기본 테스트에는 외부 서비스 계정·운영 DB·유료 서비스가 필요하지 않습니다. HTTP는 로컬 테스트 서버를 사용하며, 파일 테스트는 임시 디렉터리 또는 예제에 제공한 고정 입력을 사용합니다.

운영 서비스의 인증·권한·부하·장애 복구, 모든 운영체제의 셸 동작, 장기간의 안정성, 모든 입력과 스케줄을 확인한 것은 아닙니다. 이런 기능을 추가하거나 Go·의존성 버전을 바꿀 때는 관련 설명과 테스트·CI를 함께 갱신해야 합니다.
