# 교재 작성 지침

이 문서는 사람이 작성한 원고와 AI가 보조한 원고에 같은 기준을 적용합니다. 저장소 작업 규칙은 루트의 [`AGENTS.md`](../AGENTS.md)를 먼저 읽고, 새 장은 [공통 템플릿](../templates/chapter.md)에서 시작합니다.

## 1. 독자와 설명의 기준

기본 독자는 Go를 처음 배우는 한국어 사용자입니다. 다른 언어 경험이 없어도 첫 장부터 따라갈 수 있게 쓰되, 이미 개발 경험이 있는 독자는 학습 목표와 연습문제를 통해 필요한 부분을 골라 읽을 수 있게 합니다.

- 문장은 자연스러운 한국어로 작성합니다. 식별자와 파일명은 영어를 사용합니다.
- 새 용어는 처음 나올 때 `고루틴(goroutine)`처럼 한국어와 원어를 함께 적고, 실제 동작으로 설명합니다.
- “간단하다”, “당연하다”는 표현 대신 독자가 무엇을 확인해야 하는지 씁니다.
- 다른 언어와의 비교는 선택적인 보충 설명으로 둡니다. 특정 언어를 알아야 본문을 이해할 수 있게 만들지 않습니다.
- 이미 배운 개념을 조합합니다. 아직 배우지 않은 구문이 필요하면 최소한의 설명과 이후 학습 위치를 제공합니다.
- 한 예제에는 하나의 중심 학습 목표를 둡니다. 예제에 편의 기능을 계속 붙여 핵심이 흐려지지 않게 합니다.

## 2. 한 장의 필수 구성

| 순서 | 항목 | 반드시 담을 내용 |
| --- | --- | --- |
| 1 | 학습 목표 | 실행하거나 설명할 수 있는 행동 3~5개 |
| 2 | 사전 지식과 준비 | 앞 장, 필요한 도구·파일·외부 서비스 |
| 3 | 개념과 필요성 | 해결하려는 문제, 핵심 동작, 작은 예 |
| 4 | 실행 가능한 예제 | 소스 파일 링크, 실행 위치, 명령 |
| 5 | 예상 결과 | 출력·파일·HTTP 응답 등 관찰 가능한 결과 |
| 6 | 코드 설명 | 입력부터 출력까지의 흐름과 선택 이유 |
| 7 | 자주 하는 실수 | 증상, 원인, 확인 방법, 수정 방법 |
| 8 | 연습문제 | 확인·변형·응용의 세 수준, 완료 조건 |
| 9 | 힌트와 해설 | 문제 다음에 분리한 힌트, 해설 파일 링크 |
| 10 | 요약과 자기 점검 | 핵심 개념, 답을 보지 않고 설명할 질문 |
| 11 | 참고 자료와 다음 장 | 공식 출처, 실제로 존재하는 이동 링크 |

목차만 채운 원고를 완성된 장으로 표시하지 않습니다. 교육상 순서를 바꾸는 경우에도 위 정보는 본문에서 찾을 수 있어야 합니다.

00장처럼 환경을 준비하는 장은 구현 문제·해설을 환경 확인 실습, 문제 해결 안내와 완료 체크리스트로 대체할 수 있습니다. 확인 수준의 질문은 본문의 자기 점검에 두어도 되며, 입문 장에서 아직 배우지 않은 개념을 쓰는 응용 문제는 선택 과제로 표시합니다.

## 3. 예제와 문서를 함께 관리하기

장 번호와 주제를 `NN-topic`으로 통일합니다. 예를 들어 01장의 본문은 `book/01-first-program/README.md`, 실행 예제는 `examples/01-first-program/hello/main.go`에 둡니다.

기본 실습은 저장소 루트의 단일 Go 모듈에 포함합니다. 새 모듈이 필요한 배포·의존성 실습은 먼저 필요성을 설명하고, 실행·검사 방법을 따로 문서화합니다. 현재 구조에 장마다 `go.mod`를 만들지 않습니다.

예제는 다음 원칙을 따릅니다.

- 기본 문법과 표준 라이브러리부터 가르칩니다. 외부 패키지는 학습 목표에 필요한 경우에만 도입하고 선택 이유와 버전을 기록합니다.
- 실행 가능한 전체 코드는 소스 파일을 기준으로 합니다. 본문에 일부만 옮긴 경우 **발췌**라고 표시합니다.
- 모든 실행 명령에 작업 디렉터리를 명시하거나 “저장소 루트에서 실행”이라고 선언합니다.
- 기본 경로에는 외부 계정, 유료 서비스, 실제 개인정보, 운영 DB가 필요하지 않게 합니다.
- 파일·네트워크·데이터베이스를 쓰는 예제는 오류와 자원 정리를 함께 다룹니다.
- 서버·고루틴 예제는 종료 방법과 작업 취소 방법을 설명합니다.
- 실패를 보여 주기 위한 코드는 **의도적으로 실패하는 예**라고 표시합니다. 기본 검사 대상에 컴파일 오류나 항상 실패하는 테스트를 추가하지 않습니다.
- 결과가 달라질 수 있는 출력은 그 이유를 적습니다. 시간, 맵 순회, 동시 실행 순서 등의 값을 고정된 정답처럼 제시하지 않습니다.

프로그램 구조·오류 처리 등 언어 의미의 근거는 [Go 언어 명세](https://go.dev/ref/spec)와 [표준 라이브러리 문서](https://pkg.go.dev/std)에서 확인합니다. `go` 명령의 동작은 [공식 명령 문서](https://pkg.go.dev/cmd/go)를 참고합니다.

## 4. 설명을 검증할 수 있게 쓰기

“이렇게 쓰면 빠르다”처럼 측정이 필요한 주장은 실행 환경과 측정 방법을 함께 제공합니다. 환경을 기록하지 않은 추정치를 일반적인 성능 수치로 제시하지 않습니다.

문법 설명은 다음 세 가지를 구분합니다.

1. **언어가 보장하는 동작**: 언어 명세의 해당 절을 출처로 연결합니다.
2. **API가 약속하는 동작**: 패키지 문서에서 오류·자원 수명·동시 사용 조건을 확인합니다.
3. **이 교재의 설계 선택**: 선택 이유와 적용 범위를 설명합니다. 프로젝트의 선택을 언어 규칙으로 표현하지 않습니다.

Go 버전에 따라 달라지는 구문이나 API는 최소 버전을 적습니다. 저장소 기준 버전은 [`go.mod`](../go.mod)를 확인하고, 버전 변경은 예제·CI·설치 문서를 함께 점검합니다. 릴리스 정보는 [공식 릴리스 이력](https://go.dev/doc/devel/release)에서 확인합니다.

## 5. 연습문제·힌트·해설

연습문제는 독자가 요구사항을 읽고 자신이 완료했는지 판단할 수 있어야 합니다. 문제 파일에 입력, 출력, 제약 조건, 실행 명령 또는 확인 방법을 적습니다.

| 수준 | 목적 | 문제 형태 |
| --- | --- | --- |
| 확인 | 배운 동작을 자기 말로 설명 | 출력 예측, 오류 원인 설명, 코드 흐름 설명 |
| 변형 | 예제의 일부를 스스로 수정 | 입력·출력 변경, 조건 추가, 작은 함수 분리 |
| 응용 | 여러 개념을 조합 | 작은 기능 구현, 경계 입력 처리, 테스트 추가 |

힌트는 단계적으로 제공합니다. 첫 힌트에서 완성 코드를 바로 보여 주지 않습니다. 해설은 `solutions/`에 두고 문제 본문과 분리합니다. 해설에는 작동하는 코드뿐 아니라 선택한 이유와 대안도 짧게 설명합니다.

정답이 하나로 정해지지 않는 문제는 평가 기준을 적습니다. 예를 들어 “함수명이 해설과 같음”이 아니라 “빈 입력을 처리하고 약속한 오류를 반환함”을 확인합니다. 아직 가르치지 않은 API를 암기해야만 풀리는 문제는 해당 자료를 함께 제공합니다.

## 6. 테스트와 검토

변경한 코드가 있는 경우 루트에서 해당 패키지 테스트와 프로젝트의 기본 검사 명령을 실행합니다. 정확한 공통 명령은 [`CONTRIBUTING.md`](../CONTRIBUTING.md)를 따릅니다.

- `gofmt` 형식과 `go vet` 결과를 확인합니다.
- 단위 테스트에는 정상 입력뿐 아니라 중요한 경계·오류 입력을 포함합니다.
- 예제 테스트의 출력은 본문의 예상 출력과 일치시킵니다.
- 동시성 예제는 race detector를 지원하는 환경에서 검사합니다.
- 파일을 쓰는 테스트는 임시 디렉터리를 사용합니다. 네트워크 테스트는 가능하면 `httptest`로 재현합니다.
- 외부 DB가 필요한 통합 테스트는 실행 조건을 문서화하고 기본 단위 테스트와 구분합니다.
- 실행하지 못한 검사는 통과로 기록하지 않고 이유를 남깁니다.

문서 변경은 내부 링크, 예제 경로, 명령, 출력, 용어의 일관성을 확인합니다. 단순한 문장 수정에 불필요한 테스트를 추가하지 않습니다. 검사 범위는 바꾼 내용과 실패 위험에 맞춥니다.

## 7. 출처와 인용

공식 문서를 우선합니다. 기본 자료는 [언어 명세](https://go.dev/ref/spec), [모듈 문서](https://go.dev/ref/mod), [패키지 문서](https://pkg.go.dev/std), [Go 블로그](https://go.dev/blog/)입니다.

- 중요한 사실을 설명한 문장 가까이 관련 자료를 연결하고, 장 끝에 참고 자료를 모읍니다.
- 전체 홈페이지만 연결하기보다 해당 패키지·기능·명세 절로 연결합니다.
- 새 기능, 지원 버전, 설치 방법처럼 바뀔 수 있는 정보에는 확인 날짜를 기록합니다.
- 공식 자료의 코드를 가져오면 출처와 원문 라이선스 조건을 확인합니다. 길게 복사하기보다 직접 작성한 작은 예제로 설명합니다.
- 확인하지 않은 링크나 존재하지 않는 논문·문서를 만들지 않습니다.

## 8. 상태와 변경 기록

장 상태는 [로드맵](ROADMAP.md)의 정의를 따릅니다. 본문·예제·문제의 작성 여부와 검토 여부를 구분합니다. 목차에는 실제 존재하는 문서만 연결합니다.

새 장을 추가할 때는 다음 순서로 작업합니다.

1. 학습 목표와 앞 장에서 필요한 지식을 정합니다.
2. 작은 예제를 작성하고 실제로 실행합니다.
3. 결과를 근거로 본문·실수 사례·문제를 씁니다.
4. 힌트·해설·필요한 테스트를 추가합니다.
5. 내부 링크와 출처를 확인합니다.
6. 목차와 로드맵을 갱신하고 수행한 검사를 변경 설명에 남깁니다.

독자의 질문이나 오류 제보는 후속 개정의 근거로 활용합니다. 이미 공개한 장의 경로를 바꾸면 관련 링크도 같은 변경에서 수정합니다.
