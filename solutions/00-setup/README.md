# 00장 실습 해설: 개발 환경 확인과 문제 해결

대상 문제: [00장 환경 실습](../../exercises/00-setup/README.md)

이 해설은 환경마다 달라지는 값과 반드시 일치해야 하는 결과를 구분합니다. 자신의 사용자 이름, 설치 경로, 운영체제가 예시와 다르다는 이유만으로 잘못된 환경은 아닙니다. 아직 실습하지 않았다면 문제와 힌트를 먼저 확인하세요.

## 실습 1. 환경 기록 해설

### 명령과 출력의 대응

저장소 루트에서 실행하는 다음 명령은 네 가지 값을 순서대로 보여 줍니다.

```text
go env GOVERSION GOOS GOARCH GOMOD
```

| 출력 순서 | 의미 | 확인 기준 |
| --- | --- | --- |
| 1. `GOVERSION` | 현재 선택된 Go 도구 체인의 버전 | 저장소의 최소 버전 요구 사항을 충족하는가? |
| 2. `GOOS` | 빌드 대상 운영체제 | 실제로 실행하려는 운영체제에 맞는가? |
| 3. `GOARCH` | 빌드 대상 CPU 구조 | 실제로 실행하려는 CPU 구조에 맞는가? |
| 4. `GOMOD` | 현재 모듈의 `go.mod` 경로 | 이 저장소의 모듈 파일인가? |

예를 들어 Go 1.27.3을 사용하는 Linux x86-64 환경에서 `/work/GoLang_all_in_one`에 저장소를 두었다면 다음과 같은 결과를 볼 수 있습니다. 아래 경로는 설명을 위한 예시입니다.

```text
go1.27.3
linux
amd64
/work/GoLang_all_in_one/go.mod
```

Windows x86-64 환경에서 예시 위치가 `C:\work\GoLang_all_in_one`이라면 다음처럼 달라집니다.

```text
go1.27.3
windows
amd64
C:\work\GoLang_all_in_one\go.mod
```

macOS에서는 보통 `GOOS`가 `darwin`으로 나타납니다. ARM64 환경의 `GOARCH`는 `arm64`일 수 있습니다. 이러한 값은 운영체제의 일반적인 상품명 대신 Go 도구가 사용하는 이름입니다. `GOOS`와 `GOARCH`가 별도로 설정되어 있다면 실제 실행 환경과 다른 빌드 대상을 나타낼 수도 있습니다. 값만 보고 현재 컴퓨터의 종류를 단정하지 말고, [공식 환경 변수 설명](https://pkg.go.dev/cmd/go#hdr-Environment_variables)과 자신의 터미널 환경을 함께 확인하세요.

### 버전 판단

현재 [go.mod](../../go.mod)의 최소 Go 버전은 **1.27.0**이며, 교재에서 안내한 설치 버전은 2026-11-09에 확인한 **1.27.3**입니다. 1.27 계열의 더 새로운 패치를 설치했다면 패치 번호가 예시와 같지 않아도 됩니다. 버전 정보는 [공식 다운로드](https://go.dev/dl/)와 [릴리스 기록](https://go.dev/doc/devel/release)을 기준으로 확인합니다.

`go version`의 출력 예시는 `go version go1.27.3 linux/amd64`입니다. 운영체제와 CPU, 패치 번호는 달라질 수 있습니다. `git --version`도 `git version` 뒤의 번호가 사람마다 다를 수 있습니다. 이 실습의 기준은 도구가 정상적으로 실행되고 프로젝트의 Go 버전 요구 사항을 충족하는 것입니다.

Go는 모듈의 요구 버전과 도구 체인 설정에 따라 사용할 버전을 선택할 수 있습니다. 따라서 저장소 밖과 안에서 선택되는 버전이 항상 같다고 가정하지 않습니다. [Go Toolchains](https://go.dev/doc/toolchain)를 참고하세요.

### 실행 환경 판단

현재 폴더는 PowerShell의 `Get-Location`, Bash/Zsh의 `pwd`로 확인합니다. 이 위치가 실행 명령에서 상대 경로를 해석하는 기준입니다.

`GOOS=linux`만으로 WSL인지 원격 서버인지 알 수는 없습니다. 예를 들어 Windows에서 연 VS Code가 WSL에 연결되어 있을 수도 있고, SSH로 Linux 서버에 연결되어 있을 수도 있습니다. **어떤 터미널을 열었는지, 어디에 접속했는지, 소스 파일이 어디에 있는지**를 함께 확인하면 됩니다.

기록한 값이 다른 사람과 같아야 하는 것은 아닙니다. 자기 환경을 다음처럼 설명할 수 있으면 목표를 달성했습니다.

> “지금 터미널은 Linux 환경에서 실행 중이고, 저장소 루트에 있다. 선택된 Go 버전이 모듈의 요구 버전을 충족하며, GOMOD는 이 저장소의 go.mod를 가리킨다.”

## 실습 2. 복사·수정·실행·빌드 해설

### 수정할 파일과 결과

개인 파일은 `_practice/00-setup/main.go`입니다. 교재 원본에서 출력 문자열만 바꾸므로 전체 코드의 구조는 그대로입니다. 다음은 개인 파일에 들어갈 전체 코드입니다.

```go
package main

import "fmt"

func main() {
	fmt.Println("개발 환경 준비 완료!")
}
```

이 코드는 학습자가 개인 실습 파일에 작성하는 해설이며, 저장소에 새 실행 예제나 별도 모듈을 추가할 필요는 없습니다. 각 구문의 의미는 [01장](../../book/01-first-program/README.md)에서 자세히 다룹니다.

저장소 루트에서 다음을 실행합니다.

```text
go run ./_practice/00-setup
```

확인해야 할 정확한 출력은 다음 한 줄입니다.

```text
개발 환경 준비 완료!
```

이 실습에서는 코드에 고정한 문자열을 출력하므로 운영체제가 달라도 문장의 내용은 같습니다. 다르게 출력되면 수정한 파일을 저장했는지와 실행 대상 경로를 먼저 확인합니다. 한글이 깨졌다면 파일을 UTF-8로 저장했는지와 터미널의 문자 표시 설정을 확인합니다.

### `go fmt`의 결과

```text
go fmt ./_practice/00-setup
```

형식이 이미 맞으면 출력이 없을 수 있습니다. 형식이 바뀐 파일이 있으면 파일 경로가 출력될 수 있습니다. 포맷을 적용한 뒤 다시 실행했을 때 문장의 내용은 같아야 합니다. 포맷 명령은 줄 맞춤 등 코드 형식을 정리하기 위한 것이며 인사말을 다른 문장으로 바꾸는 명령이 아닙니다.

개인 연습 폴더는 `_`로 시작하기 때문에 `go fmt ./...`의 패키지 탐색에서 제외됩니다. 따라서 이 실습처럼 경로를 직접 지정합니다. 이는 Git의 무시 설정과 별개의 Go 도구 규칙입니다. [Go의 패키지 탐색 규칙](https://pkg.go.dev/cmd/go#hdr-Package_lists_and_patterns)을 참고하세요.

### 실행 파일의 결과

실습에서 빌드한 파일은 다음과 같습니다.

| 실행 환경 | 생성 파일 | 저장소 루트에서 실행하는 명령 |
| --- | --- | --- |
| Windows PowerShell | `bin/setup-check.exe` | `.\bin\setup-check.exe` |
| macOS·Linux·WSL | `bin/setup-check` | `./bin/setup-check` |

`go build` 자체가 인사말을 출력하지 않는 것은 정상입니다. 빌드에 성공한 뒤 생성한 실행 파일을 실행하면 `개발 환경 준비 완료!`가 출력됩니다. 빌드가 실패했다면 먼저 오류를 해결하고 다시 빌드하세요. 이미 존재하는 실행 파일을 실행했다고 해서 방금 수정한 코드의 빌드가 성공한 것은 아닙니다.

`go run`은 지정한 프로그램을 빌드하고 바로 실행하는 데 사용하며, `go build -o ...`는 지정한 이름으로 실행 파일을 만들 때 사용합니다. 이 실습에서는 같은 소스에서 나온 동작을 두 방법으로 확인했습니다. [go run](https://pkg.go.dev/cmd/go#hdr-Compile_and_run_Go_program)과 [go build](https://pkg.go.dev/cmd/go#hdr-Compile_packages_and_dependencies)의 공식 설명을 참고합니다.

## 실습 3. 잘못된 실행 위치 해설

### 왜 `go run .`은 실패했을까?

이 저장소 루트에는 모듈 설정 파일인 `go.mod`가 있지만, 바로 실행할 Go 소스 파일은 없습니다. 따라서 루트에서 `go run .`을 실행하면 현재 폴더를 실행 대상으로 삼다가 실패합니다. 오류는 Go 파일이 없다는 취지이며, 구체적인 문구와 경로는 환경에 따라 달라집니다.

실패 원인은 Go 설치 자체가 아니라 **실행 대상으로 선택한 폴더**입니다. 루트에 새 `main.go`나 별도 `go.mod`를 만드는 것으로 해결할 필요도 없습니다.

### 올바른 대상 지정

저장소 루트에서 교재 원본을 실행하려면 다음 명령을 사용합니다.

```text
go run ./examples/01-first-program/hello
```

출력:

```text
안녕하세요, Go!
```

같은 위치에서 개인 실습 파일을 실행하려면 다음 명령을 사용합니다.

```text
go run ./_practice/00-setup
```

출력:

```text
개발 환경 준비 완료!
```

두 명령은 같은 모듈 안에서 서로 다른 패키지를 실행합니다. 출력이 다른 이유는 각 폴더의 `main.go`가 서로 다른 문자열을 출력하기 때문입니다.

반대로 해당 예제 폴더 안으로 이동한 상태라면 `go run .`이 정상적으로 동작합니다. `.`이라는 표기 자체가 잘못된 것은 아닙니다. 그 표기가 가리키는 현재 폴더에 실행할 패키지가 있는지가 중요합니다. 이 교재는 경로 혼동을 줄이려고 기본 명령을 저장소 루트 기준으로 안내합니다.

## 본문의 자기 점검 해설

[00장 본문](../../book/00-setup/README.md) 마지막에 제시한 다섯 질문의 해설입니다.

1. **Windows 설치와 원격 Linux는 별개입니다.** SSH 터미널에서 실행할 Go는 서버에 준비되어 있어야 합니다. 로컬 설치가 자동으로 서버에 복사되는 것은 아닙니다.
2. **GOMOD만으로 현재 폴더가 루트인지 알 수는 없습니다.** 하위 패키지에서도 상위의 같은 `go.mod`를 찾을 수 있습니다. 현재 폴더는 `Get-Location` 또는 `pwd`로 확인합니다.
3. **점은 현재 폴더, 명시한 경로는 그 위치를 기준으로 찾을 예제 폴더입니다.** 이 저장소 루트의 `go run .`은 실패하지만, 루트에서 `go run ./examples/01-first-program/hello`는 예제 패키지를 실행합니다.
4. **파일 저장, 빌드 성공 여부와 실행 파일 경로를 확인합니다.** 소스를 수정한 뒤 기존 실행 파일을 실행하려면 다시 빌드해야 합니다. 이전 빌드가 남아 있거나 다른 파일을 실행했을 수도 있습니다.
5. **Go의 `./...` 탐색은 `_practice`를 제외합니다.** 개인 코드는 해당 패키지 경로를 명시해 실행·검사합니다. 이는 Git의 `.gitignore`와는 별개의 규칙입니다.

## 실습 문서의 자기 점검 해설

| 질문 | 설명할 수 있어야 할 핵심 |
| --- | --- |
| 터미널은 어디서 실행 중인가? | 로컬·WSL·원격 여부와 실제 운영체제를 함께 확인한다. |
| 현재 작업 폴더는 무엇인가? | 상대 경로를 해석하는 기준이며 `Get-Location` 또는 `pwd`로 확인한다. |
| 모듈 루트와 패키지 폴더가 달라도 되는가? | 그렇다. 이 저장소는 루트 모듈 하나 안에 여러 실행 예제 패키지를 둔다. |
| 실행과 빌드는 어떻게 다른가? | `go run`은 빌드 후 바로 실행하고, `go build`로 만든 파일은 따로 실행한다. |
| 개인 폴더의 검사 경로를 왜 지정하는가? | `_practice`는 Go의 `./...` 탐색 대상에서 제외되기 때문이다. |

설치 프로그램을 다시 실행하거나 전역 설정을 바꾸기 전에 **명령, 현재 폴더, Go 버전, 실행 대상**을 확인하는 습관을 익히는 것이 이번 실습의 핵심입니다.
