# 26장 연습문제 — 성능 측정과 진단

[본문](../../book/26-performance/README.md)을 읽고 정확성과 측정 범위를 함께 확인합니다.
이번 문제의 목표는 특정 CPU에서 정해진 숫자를 얻는 것이 아닙니다.
같은 동작을 수행하는 구현을 준비하고, 비교 조건과 관찰 결과를 설명하는 것이 목표입니다.

## 준비와 제출 자료

모든 명령은 저장소 루트에서 실행합니다.
개인 코드는 `_practice/26-performance/` 아래에 두며,
참고 구현과 테스트를 덮어쓰지 않습니다.

| 문제 | 수준 | 남길 결과 |
| --- | --- | --- |
| 1 | 확인 | 지표 해석과 결론의 한계 |
| 2 | 확인·변형 | 잘못된 측정 범위의 수정 계획 |
| 3 | 변형 | 구분자를 넣는 함수와 테스트·벤치마크 |
| 4 | 변형 | 양수 필터 두 구현과 분포별 측정 |
| 5 | 응용 | 일괄 조회와 생성 비용을 나눈 측정 |
| 6 | 응용 | 독립 바이트 복사와 크기별 벤치마크 |
| A | 선택 | 프로파일을 포함한 한 페이지 실험 기록 |

Go 버전은 루트 `go.mod`를 따릅니다.
처음 작업할 때 아래처럼 함수 구현을 위한 파일을 준비할 수 있습니다.
기존 파일은 그대로 두므로 다시 실행해도 작성한 코드를 덮어쓰지 않습니다.

PowerShell:

```powershell
$names = @("join-separated", "positive", "query-batch", "prefix")
foreach ($name in $names) {
    $dir = "_practice/26-performance/$name"
    New-Item -ItemType Directory -Force $dir | Out-Null
    if (-not (Test-Path "$dir/main.go")) {
        Copy-Item examples/01-first-program/hello/main.go "$dir/main.go"
    }
}
```

Bash:

```sh
for name in join-separated positive query-batch prefix; do
    dir="_practice/26-performance/$name"
    mkdir -p "$dir"
    if [ ! -e "$dir/main.go" ]; then
        cp examples/01-first-program/hello/main.go "$dir/main.go"
    fi
done
```

필요한 `main_test.go`는 각 디렉터리에 직접 작성합니다.
측정 결과는 코드 파일의 기대 출력에 하드코딩하지 않고 별도 메모에 기록하세요.

## 문제 1. 시간과 메모리 지표 해석

아래는 **계산 연습을 위한 가상의 결과**입니다.
같은 입력과 반환 계약을 가진 두 구현을 비교했다고 가정합니다.
실제 저장소에서 측정한 수치가 아닙니다.

| 구현 | ns/op | B/op | allocs/op |
| --- | ---: | ---: | ---: |
| A | 1000 | 800 | 5 |
| B | 800 | 1200 | 2 |

### 요구사항

1. 각 열이 한 번의 작업에 대해 무엇을 나타내는지 설명합니다.
2. B의 시간 감소율을 계산합니다.
3. B가 “메모리를 무조건 적게 쓴다”고 말할 수 없는 이유를 설명합니다.
4. 전체 HTTP 요청 시간이 20% 줄었다고 결론 내릴 수 있는지 판단합니다.
5. 실제 채택 전에 추가할 조건 두 개를 적습니다.

### 완료 조건

시간, 할당 바이트, 할당 횟수를 서로 구분해야 합니다.
한 함수의 평균과 전체 서비스의 지연을 같은 지표로 취급하지 않아야 합니다.

<details>
<summary>힌트 1</summary>

감소율의 기준은 원래 값 A입니다.
할당 한 번의 크기는 같다고 보장되지 않습니다.

</details>

<details>
<summary>힌트 2</summary>

B는 할당 횟수가 적어도 한 번에 더 큰 객체를 만들 수 있습니다.
반복 측정과 실제 입력 분포를 추가 조건으로 생각해 보세요.

</details>

## 문제 2. 측정 범위가 다른 코드 찾기

본문 `lookup/main_test.go`의 세 벤치마크를 읽습니다.
다음 요구를 가진 서비스에 어떤 측정이 더 가까운지 설명하세요.

- 서비스 P: 시작할 때 목록을 읽고 맵을 만든 뒤, 요청마다 한 번 조회합니다.
- 서비스 Q: 요청마다 새로운 목록을 받고 맵을 만든 뒤, 한 번 조회합니다.
- 서비스 R: 한 목록을 받은 뒤 같은 목록에 대해 1000번 조회합니다.

### 요구사항

1. 각 서비스에서 생성 비용을 포함하거나 제외할 이유를 적습니다.
2. R의 “한 번의 작업”을 정의합니다.
3. `LinearMissing`에 첫 원소를 찾는 입력을 넣었다면 이름과 해석을 어떻게 고칠지 적습니다.
4. 잘못된 결론의 예 한 개와 수정한 문장을 적습니다.

### 완료 조건

루프 안팎의 위치를 취향으로 결정하지 않고 실제 사용 방식과 연결해야 합니다.
서비스 R에서는 “조회 한 번”과 “1000개 일괄 조회”를 구분해야 합니다.

<details>
<summary>힌트</summary>

준비 비용이 사라지는 것이 아니라 다른 시점에 지불되는 것입니다.
최종 사용자가 기다리는 범위가 무엇인지 먼저 정의하세요.

</details>

## 문제 3. 구분자가 있는 문자열 결합

다음 함수를 작성합니다.

```go
func joinSeparated(parts []string, sep string) string
```

함수는 모든 원소를 순서대로 연결하되 **원소 사이에만** 구분자를 넣습니다.
`strings.Builder`를 사용하고, 호출 사이에 전역 상태를 공유하지 않습니다.

### 입력·출력 계약

| parts | sep | 반환값 |
| --- | --- | --- |
| `nil` | `","` | `""` |
| `[""]` | `","` | `""` |
| `["", ""]` | `","` | `","` |
| `["a", "b"]` | `""` | `"ab"` |
| `["가", "나"]` | `" / "` | `"가 / 나"` |

`main`은 `[]string{"한글", "Go", "측정"}`과 `","`를 사용합니다.

```text
한글,Go,측정
```

### 테스트와 측정

정확성 테스트는 위 표를 포함하고 `strings.Join`과 비교합니다.
벤치마크 입력은 `"Go"` 원소 10개와 100개로 나누세요.
원소 배열 준비는 루프 밖에서 수행하고, 결합 한 번만 측정합니다.

```sh
go test -count=1 ./_practice/26-performance/join-separated
go test -run '^$' -bench . -benchmem -count=3 ./_practice/26-performance/join-separated
```

### 완료 조건

- 끝에 구분자가 붙지 않습니다.
- 빈 원소가 있어도 원소 수에 따른 구분자를 유지합니다.
- 테스트 통과 후 크기별 측정 결과를 기록합니다.
- 사용을 시작한 Builder를 값으로 복사하지 않습니다.

<details>
<summary>힌트 1</summary>

원소 내용이 빈 문자열인지보다 원소의 인덱스가 0인지 먼저 생각합니다.

</details>

<details>
<summary>힌트 2</summary>

첫 원소가 아니면 구분자를 쓰고, 그 뒤에 현재 원소를 씁니다.

</details>

## 문제 4. 양수 필터의 예약량

두 함수를 작성합니다.

```go
func positivesGrow(values []int) []int
func positivesReserve(values []int) []int
```

0보다 큰 원소만 입력 순서대로 반환합니다.
입력을 수정하지 않고 결과 원소를 수정해도 입력이 바뀌지 않게 합니다.
첫 함수는 빈 슬라이스에서, 두 번째는 `len(values)`만큼 용량을 준비해 시작합니다.

### 입력·출력 계약

| 입력 | 반환 원소 |
| --- | --- |
| `nil` | 없음 |
| `[-1, 0]` | 없음 |
| `[2, 2]` | `[2, 2]` |
| `[-2, 3, 0, 5, -1]` | `[3, 5]` |

결과가 `nil`인지 비어 있는 비nil 슬라이스인지는 이 문제의 계약에 넣지 않습니다.
길이와 원소, 순서, 입력 보존을 비교하세요.

`main`의 출력:

```text
[3 5]
[3 5]
```

### 측정 조건

길이 1000의 입력에서 다음 세 분포를 만듭니다.

1. 모두 양수.
2. 짝수 인덱스의 원소만 양수, 나머지는 0.
3. 인덱스가 100의 배수인 원소만 양수, 나머지는 0.

각 양수 원소는 `i+1`로 둡니다.
원소 생성은 측정 루프 밖에 두고, 같은 입력을 두 구현에 사용하세요.

### 완료 조건

테스트와 측정 결과에 더해 다음 질문에 답합니다.

- 양수가 적을 때 최대 길이 예약의 단점은 무엇인가요?
- 할당 횟수 감소가 바이트 감소도 뜻하나요?
- 입력과 결과가 같은 배열을 공유하지 않는지 어떻게 검사했나요?

<details>
<summary>힌트</summary>

정확성은 `slices.Equal`과 입력 복사본으로 확인할 수 있습니다.
측정 이름에는 `All`, `Half`, `Sparse`처럼 분포를 드러내세요.

</details>

## 문제 5. 일괄 조회의 세 가지 비용

자료 목록과 조회 목록을 받아 성공한 **조회 횟수**를 셉니다.
자료에 같은 값이 여러 번 있어도 한 조회는 최대 한 번만 성공합니다.
조회 목록에 같은 값이 여러 번 있으면 각각 별도의 조회입니다.

### 함수 계약

```go
func hitsLinear(values, queries []int) int
func index(values []int) map[int]struct{}
func hitsIndexed(set map[int]struct{}, queries []int) int
```

| 자료 목록 | 조회 목록 | 성공 횟수 |
| --- | --- | ---: |
| `nil` | `[0]` | 0 |
| `[1]` | `nil` | 0 |
| `[1, 1, 2]` | `[1, 1, 3]` | 2 |
| `[2, 4, 6]` | `[4, 5, 4]` | 2 |

`main`은 마지막 행을 사용합니다.

```text
선형: 2
인덱스: 2
```

### 벤치마크 요구사항

자료는 0~999, 조회는 `[0, 500, 999, 1001]`로 고정합니다.
다음 세 하위 벤치마크를 작성합니다.

- `Linear`: 슬라이스에서 네 번 조회.
- `Prepared`: 이미 만든 맵에서 네 번 조회.
- `BuildIncluded`: 새 맵을 만들고 네 번 조회.

### 완료 조건

측정 루프 한 번이 네 조회를 모두 처리한다는 점을 문서화합니다.
처리량을 계산할 때 일괄 작업 수와 개별 조회 수를 혼동하지 않습니다.
세 구현의 성공 횟수가 같은지 테스트합니다.

<details>
<summary>힌트</summary>

선형 구현에서 자료의 중복 때문에 횟수가 늘지 않도록 찾으면 안쪽 반복을 끝냅니다.
맵은 키 중복을 자동으로 합치지만 조회 목록의 반복까지 없애지는 않습니다.

</details>

## 문제 6. 앞부분을 독립된 바이트로 복사

다음 함수를 작성합니다.

```go
func clonePrefix(data []byte, n int) ([]byte, error)
```

`0 <= n <= len(data)`이면 앞의 `n`바이트를 독립된 결과로 반환합니다.
`n=0`이면 `nil, nil`을 반환합니다.
범위를 벗어나면 `nil`과 길이 오류를 반환합니다.

이 함수는 바이트 단위 함수입니다.
한글 문자의 중간을 잘라도 자동으로 문자 경계를 보정하지 않습니다.
텍스트 처리가 필요하면 07장의 UTF-8 계약을 별도로 적용해야 합니다.

### 경계 입력

| data | n | 결과 |
| --- | ---: | --- |
| `"Go!"` | -1 | 오류 |
| `"Go!"` | 0 | nil, 오류 없음 |
| `"Go!"` | 2 | `"Go"` |
| `"Go!"` | 3 | `"Go!"` |
| `"Go!"` | 4 | 오류 |

`main`에서 원본을 `"Go!"`로 만들고 두 바이트를 복사한 뒤,
원본 첫 바이트를 `'N'`으로 바꾸세요.

```text
prefix=Go
source=No!
```

### 측정 조건

입력은 길이 4096의 바이트 슬라이스입니다.
32, 256, 4096바이트를 복사하는 하위 벤치마크를 작성합니다.
`ReportAllocs`와 `SetBytes`를 설정하고 오류가 나면 측정을 실패시킵니다.

### 완료 조건

- 범위 오류와 빈 결과를 구분합니다.
- 반환 결과를 바꿔도 원본은 보존됩니다.
- 복사량을 `SetBytes`에 넣습니다.
- 벤치마크가 장기 보유 메모리 실험과 다른 이유를 설명합니다.

<details>
<summary>힌트</summary>

범위를 먼저 검사한 뒤 `bytes.Clone` 또는 `make`와 `copy`로 복사합니다.
`data[:n]`만 반환하면 독립성 계약을 지키지 못합니다.

</details>

## 선택 A. 프로파일을 포함한 실험 기록

문제 3~6 중 하나를 골라 본문 방식으로 CPU·메모리 프로파일을 수집합니다.
표본이 부족하면 입력 또는 측정 시간을 늘리고 그 조건을 기록합니다.

보고서에는 다음을 포함합니다.

1. 입력·출력·오류 계약.
2. Go 버전, OS, CPU, 측정 명령.
3. 비교 구현과 포함·제외한 준비 비용.
4. 반복 측정 결과와 `flat`·`cum` 관찰.
5. 변경 전후 정확성 테스트 결과.
6. 채택 여부와 그 이유, 추가로 필요한 검증.

실제 개선이 없다는 결론도 근거가 명확하면 완성된 실험입니다.
프로파일에 보이지 않은 함수를 비용이 0인 함수라고 단정하지 않습니다.
