## 문제 1. 데이터 레이스와 논리 오류 구분

**수준: 확인**

다음 설명이 맞는지 판단하고 이유를 적습니다.

1. 마지막에 Wait를 호출하면 작업들이 같은 count를 ++해도 안전하다.
2. 쓰는 메서드만 잠그면 읽는 메서드는 잠그지 않아도 된다.
3. atomic Load와 Store를 사용한 모든 코드는 논리적으로 정확하다.
4. 잠금을 잡은 상태의 구조체를 값으로 복사해도 같은 잠금이 유지된다.
5. RWMutex의 RLock을 잡았으므로 원본 맵에 써도 된다.
6. Snapshot이 새 맵을 반환하면 값이 포인터여도 항상 완전히 독립적이다.
7. OnceValues는 일시적 오류가 사라질 때까지 다음 호출에서 재시도한다.
8. race detector가 통과하면 한도 초과나 잘못된 이체도 없다는 뜻이다.

### 추가 과제

두 작업이 다음 코드를 실행할 때 결과 증가가 하나 사라지는 순서를 표로 적습니다.

```go
old := counter.Load()
counter.Store(old + 1)
```

이것이 데이터 레이스 없이도 잘못될 수 있는 이유를 설명합니다.

### 힌트

한 연산의 원자성과 여러 연산 묶음의 원자성을 구분합니다.
최종 결과가 우연히 맞는 실행만으로 판단하지 않습니다.

## 문제 2. 재고를 넘기지 않는 예약

**수준: 변형**

개인 폴더: `_practice/20-sync/inventory`

```go
func newInventory(stock int) (*Inventory, error)
func (i *Inventory) Reserve(quantity int) bool
func (i *Inventory) Remaining() int
```

### 계약

| 항목 | 규칙 |
| --- | --- |
| 시작 재고 | 0~10000 |
| 예약 수량 | 1~100 |
| 잘못된 예약 수량 | false, 상태 변경 없음 |
| 재고 부족 | false, 상태 변경 없음 |
| 성공 | 수량만큼 차감, true |
| 불변 조건 | 재고는 음수가 되지 않음 |
| 동시 사용 | Reserve와 Remaining을 동시에 호출 가능 |

재고 10에 수량 1 예약을 20개 고루틴에서 시도합니다.
성공한 작업의 인덱스는 정해지지 않지만 성공 개수는 10이어야 합니다.

```text
예약 성공: 10
남은 재고: 0
```

### 필수 테스트

- 잘못된 시작 재고 -1, 10001.
- 예약 수량 -1, 0, 101.
- 재고가 충분할 때와 부족할 때.
- 재고 1000에서 7개 예약을 충분히 많이 동시에 시도.
- 마지막 테스트의 성공 횟수 142, 남은 재고 6.
- 실패한 예약 전후의 재고가 같음.

### 힌트

재고 확인과 차감을 같은 Lock 구간에 둡니다.
Remaining의 읽기도 같은 잠금을 사용합니다.
잠금이 들어 있는 Inventory는 사용 후 복사하지 않습니다.

## 문제 3. 잠금 없이 안전한 지역 빈도 집계

**수준: 응용**

개인 폴더: `_practice/20-sync/local-frequency`

```go
func countWords(parts [][]string) (map[string]int, error)
```

단어 묶음마다 작업자 하나를 시작합니다.
각 작업자는 자신의 지역 맵을 만들고,
호출자가 모든 작업자를 기다린 뒤 맵들을 합칩니다.

### 입력 계약

| 항목 | 범위 |
| --- | --- |
| 묶음 수 | 0~8 |
| 전체 단어 수 | 최대 1000 |
| 단어 원문 길이 | 최대 64바이트 |
| 인코딩 | 유효한 UTF-8 |
| 공백 제거 후 빈 단어 | 오류 |
| 정규화 | TrimSpace 뒤 ToLower |

빈 입력은 빈 맵과 nil 오류입니다.
오류면 nil 맵과 오류를 반환합니다.
검증은 작업을 시작하기 전에 모두 마칩니다.

입력:

```text
[["Go","test"],["go","한글"],[" test ","GO"]]
```

출력은 키를 정렬해 다음처럼 표시합니다.

```text
go: 3
test: 2
한글: 1
```

### 금지 사항

모든 작업자가 같은 map에 동시에 쓰지 않습니다.
`map[string]int`를 sync.Map으로 단순 치환해 문제를 해결하지 않습니다.
이 문제의 목표는 **공유 쓰기 자체를 없애는 것**입니다.

### 필수 테스트

- 대소문자와 앞뒤 공백의 정규화.
- 한글과 중복 단어.
- 빈 입력과 빈 묶음.
- 잘못된 UTF-8과 공백뿐인 단어.
- 65바이트 단어와 9개 묶음.
- 전체 단어 1001개.

### 힌트

지역 맵을 담는 슬라이스의 각 인덱스를 한 작업자에게 맡깁니다.
최종 결과 맵은 Wait 뒤의 호출자만 수정합니다.

## 문제 4. 실패까지 한 번만 읽는 설정

**수준: 응용**

개인 폴더: `_practice/20-sync/cached-loader`

```go
type Config struct { Workers int }
func newLoader(load func() (Config, error)) (*Loader, error)
func (l *Loader) Get() (Config, error)
```

### 계약

- nil load는 생성 오류입니다.
- 처음 Get이 실행될 때만 실제 load를 호출합니다.
- 여러 Get이 동시에 호출되어도 실제 load는 한 번입니다.
- Workers는 1~32여야 합니다.
- load 오류 또는 설정 검증 오류는 Config 영값과 함께 반환합니다.
- 그 오류는 이후 Get에서도 보존합니다.
- 원래 오류는 errors.Is로 확인할 수 있어야 합니다.
- 자동 재시도나 실행 중 설정 갱신 기능은 제공하지 않습니다.

실제 load가 항상 sentinel 오류를 반환하도록 만듭니다.
세 작업에서 Get을 호출합니다.

```text
읽기 시도: 1
같은 오류 보존: true
```

### 필수 테스트

- 정상 설정을 여러 작업에서 읽음.
- 원래 오류를 16개 작업에서 모두 확인함.
- 잘못된 Workers 0과 33.
- nil load.
- 오류가 난 뒤 다시 Get해도 load 호출 횟수가 늘지 않음.

### 힌트

`sync.Once`와 필드에 저장한 값·오류를 사용하거나,
`sync.OnceValues`를 감싼 함수를 사용할 수 있습니다.
초기화 전에 값을 읽는 경로가 없어야 합니다.

### 설계 질문

일시적인 파일 접근 실패 후 다시 읽는 요구가 추가되면
현재 도구를 그대로 사용해도 될까요?
Once의 목적과 재시도의 목적이 다른 이유를 적습니다.

## 문제 5. 중복 반납을 막는 슬롯 제한

**수준: 응용**

개인 폴더: `_practice/20-sync/atomic-slots`

```go
func newSlots(limit int64) (*Slots, error)
func (s *Slots) TryAcquire() (release func(), ok bool)
```

동시에 사용할 수 있는 슬롯을 1~32개로 제한합니다.
성공하면 나중에 슬롯을 반납하는 함수를 반환합니다.
실패하면 nil 함수와 false를 반환합니다.

### 계약

| 상황 | 결과 |
| --- | --- |
| 여유 있음 | active를 하나 늘리고 반납 함수 반환 |
| 가득 참 | 기다리지 않고 false |
| 반납 함수 첫 호출 | active 하나 감소 |
| 같은 반납 함수를 다시 호출 | 추가 감소 없음 |
| 같은 반납 함수를 동시에 여러 번 호출 | 감소는 정확히 한 번 |
| 불변 조건 | 0 <= active <= limit |

limit은 생성 뒤 바뀌지 않습니다.
획득에는 CAS를 사용하고,
반납 함수의 중복 실행 방지에는 Once를 조합할 수 있습니다.

limit 2에서 세 번 획득한 뒤,
첫 반납 함수를 두 번 실행하고 다시 획득합니다.
모든 성공한 획득을 반납한 뒤 출력합니다.

```text
처음 세 요청: true true false
반납 후 획득: true
남은 사용량: 0
```

### 필수 테스트

- 한도를 넘는 세 번째 요청이 실패.
- 첫 반납 함수를 8개 고루틴이 호출해도 사용량은 하나만 감소.
- 다시 획득한 슬롯도 정상 반납.
- 여러 작업의 반복 획득·반납 뒤 사용량 0.
- limit 0과 33 거부.

### 힌트

CAS 성공으로 획득한 순간에 해당 획득만의 Once를 만듭니다.
Slots 전체에 Once 하나를 두면 모든 슬롯 중 첫 반납만 처리하는 잘못된 구조가 됩니다.

### 적용 범위

이 함수는 기다리는 큐나 공정한 접수 순서를 제공하지 않습니다.
실패한 호출자는 재시도·거절·대기 중 어떤 정책을 쓸지 별도로 정해야 합니다.
성공 후 release를 호출하지 않으면 슬롯은 계속 사용 중으로 남습니다.

## 문제 6. 보호 범위 검토

**수준: 확인·응용**

다음 상황의 문제를 설명합니다.

1. Transfer가 출금 잔액을 읽고 잠금을 푼 뒤 나중에 차감한다.
2. Snapshot이 내부 map을 그대로 반환한다.
3. Report가 잠금을 잡은 채 사용자 콜백을 부르고 그 콜백이 Add를 부른다.
4. 반복 안에서 Lock 후 defer Unlock을 등록한다.
5. 한 작업은 A→B 순서로 잠그고 다른 작업은 B→A 순서로 잠근다.
6. Lock을 별도 고루틴에서 시작하고 Context가 취소되면 호출자만 반환한다.

각 항목에 다음을 적습니다.

- 문제가 되는 두 사건.
- 지켜야 할 불변 조건 또는 수명 계약.
- 수정할 구조.
- 어떤 테스트로 관찰할 수 있는지.

실제 레이스나 무한 교착을 기본 테스트에 추가하지 않습니다.
올바른 구현의 정상·경계 동작을 테스트하고 실패 구조는 설명용 발췌로 남깁니다.

## 문제 7. 선택 — Mutex와 RWMutex 측정 계획

같은 Store를 Mutex 버전과 RWMutex 버전으로 만듭니다.
이 단계에서는 성능 우열을 추측해 결론 내리지 않습니다.
[26장](../../book/26-performance/README.md)을 읽은 뒤 다음 조건을 비교합니다.

- 읽기 100%, 읽기 90%·쓰기 10%, 읽기 50%·쓰기 50%.
- 고루틴 수와 데이터 크기.
- 임계 구간의 작업량.
- 할당과 측정 반복 수.

결과에는 Go 버전·OS·CPU·명령·반복 조건을 함께 적습니다.
레이스 검사 실행의 시간과 일반 성능 측정의 시간을 직접 비교하지 않습니다.
