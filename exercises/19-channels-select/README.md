# 19장 연습문제 — 채널과 select

[본문](../../book/19-channels-select/README.md)의 전달·닫기·취소를 연습합니다.

[해설](../../solutions/19-channels-select/README.md)은 구현한 뒤 확인합니다.

## 준비

모든 명령은 저장소 루트에서 실행합니다.
각 문제는 `_practice/19-channels-select/문제이름/`에 작성합니다.
기존 개인 파일을 덮어쓰지 않습니다.

New-Item -ItemType Directory -Force _practice/19-channels-select/filter-positive | Out-Null
if (-not (Test-Path _practice/19-channels-select/filter-positive/main.go)) {
    Copy-Item examples/19-channels-select/pipeline/main.go _practice/19-channels-select/filter-positive/main.go

각 채널에 대해 다음 네 가지를 코드 옆에 메모합니다.

| 질문 | 답할 내용 |
| --- | --- |
| 전송자 | 한 명인지 여러 명인지 |
| 수신자 | 어디에서 얼마나 오래 읽는지 |
| 닫는 주체 | 마지막 전송이 끝났음을 누가 아는지 |
| 종료 확인 | Wait·완료 신호·함수 반환 중 무엇인지 |

## 문제 1. 채널 상태표와 선택 예측

**수준: 확인**

다음 표를 채웁니다.

| 상태 | 전송 | 수신 | close |
| --- | --- | --- | --- |
| nil 채널 | 직접 작성 | 직접 작성 | 직접 작성 |
| 열린 버퍼 없는 채널, 상대 없음 | 직접 작성 | 직접 작성 | 직접 작성 |
| 버퍼가 가득 찬 열린 채널 | 직접 작성 | 직접 작성 | 직접 작성 |
| 닫혔지만 버퍼에 값 있음 | 직접 작성 | 직접 작성 | 직접 작성 |
| 닫혔고 버퍼도 비었음 | 직접 작성 | 직접 작성 | 직접 작성 |

다음 질문에 답합니다.

1. 닫힌 int 채널에서 0을 받았다는 사실만으로 정상 0과 종료를 구분할 수 있나요?
2. select에 준비된 입력이 두 개 있으면 첫 case가 항상 선택되나요?
3. default가 있는 select를 빈 for 안에서 돌리면 어떤 문제가 생기나요?
4. 버퍼 용량을 늘리면 소비자의 조기 반환 문제를 항상 해결할 수 있나요?
5. 모든 채널을 반드시 닫아야 하나요?
6. 채널로 슬라이스를 보내면 내부 배열도 독립적으로 복사되나요?
7. 송신 전용 타입을 받는 함수 두 개가 같은 채널을 각각 닫아도 되나요?

### 힌트

닫힌 채널은 더 보내지 못하지만 받을 수 있습니다.
nil 채널과 닫힌 채널은 수신에서 정반대에 가까운 동작을 보입니다.

## 문제 2. 양수만 통과시키는 단계

**수준: 변형**

개인 폴더: `_practice/19-channels-select/filter-positive`

```go
func positive(ctx context.Context, values []int) ([]int, error)
```

입력 슬라이스를 채널로 보내는 단계와 양수만 통과시키는 단계를 만듭니다.
소비자는 모든 양수를 모아 반환합니다.

| 항목 | 계약 |
| --- | --- |
| 입력 길이 | 0~1000 |
| 값의 범위 | int 전체; 산술 계산 없이 양수 여부만 판단 |
| 출력 순서 | 입력에서 양수가 등장한 순서 |
| 0과 음수 | 결과에서 제외 |
| 빈 입력 | 빈 결과와 nil 오류 |
| 이미 취소된 Context | nil 결과와 취소 오류 |
| 진행 중 취소 | 모든 내부 작업 종료 후 nil 결과와 취소 오류 |
| 채널 닫기 | 각 단계가 자신의 출력만 닫음 |

입력 `[-1, 2, 0, 3]`의 예상 출력:

```text
양수: [2 3]
```

### 필수 테스트

- 빈 입력과 양수가 하나도 없는 입력.
- 입력 순서가 3, 1일 때 출력도 3, 1.
- 같은 양수가 여러 번 있으면 개수를 보존.
- 허용 상한 1000개와 초과 1001개.
- 이미 취소된 Context.

### 완료 조건

입력 전송과 필터의 출력 전송 모두 취소로 빠져나와야 합니다.
수신자가 생산자의 입력 채널을 닫으면 안 됩니다.
함수 반환 뒤 내부 고루틴이 결과에 계속 접근하면 안 됩니다.

### 힌트

전송이 포함된 모든 줄을 찾습니다.
그 줄에서 상대가 더 이상 받지 않으면 어떻게 끝날지 설명할 수 있어야 합니다.

## 문제 3. 앞의 N개까지만 받기

**수준: 변형**

개인 폴더: `_practice/19-channels-select/take-values`

```go
func take(ctx context.Context, in <-chan int, limit int) ([]int, error)
```

채널에서 최대 limit개의 값을 받아 반환합니다.
이 함수는 입력 채널을 만들지 않으며 입력 생산자의 수명을 소유하지 않습니다.

### 계약

- limit은 0~1000입니다. 잘못된 limit은 오류입니다.
- 채널이 먼저 닫히면 지금까지 받은 값을 정상 결과로 반환합니다.
- limit이 0이면 빈 결과를 반환합니다.
- 입구 또는 수신 중 취소되면 nil 결과와 ctx.Err를 반환합니다.
- 입력 채널은 닫지 않습니다.
- 이 함수 내부에서는 별도 고루틴을 만들 필요가 없습니다.
- nil 입력과 양수 limit이면 취소나 마감이 올 때까지 기다릴 수 있습니다.

버퍼에 1, 2, 3, 4를 넣고 닫은 뒤 limit 2로 호출합니다.
그 다음 원래 입력에서 한 번 더 받아 봅니다.

```text
받은 값: [1 2]
남은 첫 값: 3
```

### 필수 테스트

| 입력 | limit | 결과 |
| --- | --- | --- |
| [1,2], 이미 닫힘 | 0 | 빈 결과 |
| [1,2], 이미 닫힘 | 1 | [1] |
| [1,2], 이미 닫힘 | 3 | [1,2] |
| nil 입력, 이미 취소된 Context | 1 | 취소 오류 |
| 임의 입력 | -1 또는 1001 | 입력 오류 |

### 수명에 대한 질문

take가 2개만 받고 반환했다면 생산자는 누가 중단해야 하나요?
생산자가 별도 고루틴이라면 호출자가 취소하고 기다려야 합니다.
take가 반환했다는 사실만으로 외부 생산자까지 종료했다고 보고하지 않습니다.

### 힌트

각 반복에서 ctx.Done과 입력 수신을 함께 선택합니다.
값을 받았을 때는 ok도 확인합니다.
채널 방향이 수신 전용이므로 닫기를 넣으려 하면 타입 단계에서도 문제가 드러납니다.

## 문제 4. 여러 묶음의 결과 모으기

**수준: 응용**

개인 폴더: `_practice/19-channels-select/merge-results`

```go
func collect(ctx context.Context, parts [][]int) ([]int, error)
```

각 묶음마다 생산자를 하나 만들고 같은 출력 채널로 값을 보냅니다.
수신자는 한 곳에서 값을 모아 오름차순으로 반환합니다.

| 항목 | 계약 |
| --- | --- |
| 묶음 수 | 최대 8 |
| 전체 원소 수 | 최대 1000 |
| 빈 묶음 | 허용 |
| 중복값 | 보존 |
| 결과 순서 | 오름차순 |
| 취소 | 모든 생산자 종료 후 nil 결과와 취소 오류 |
| 출력 닫기 | 모든 생산자를 기다린 담당자 한 명 |

입력 `[[3,1],[2,3],[]]`의 출력:

```text
모은 값: [1 2 3 3]
```

### 필수 테스트

- 입력 묶음이 아예 없는 경우.
- 빈 묶음만 있는 경우.
- 중복값이 다른 묶음에 들어 있는 경우.
- 8개 묶음과 9개 묶음.
- 전체 1000개와 1001개.
- 이미 취소된 Context.

### 금지 사항

각 생산자가 같은 out을 defer close하면 안 됩니다.
여러 생산자가 같은 결과 슬라이스에 append해서도 안 됩니다.

### 힌트

생산자들은 값 전송만 담당합니다.
모든 생산자를 기다린 담당자가 out을 닫습니다.
소비자는 out이 닫힐 때까지 모으고 담당자의 종료도 확인합니다.

## 문제 5. 조기 중단 누수 수정하기

**수준: 응용·검토**

다음은 **의도적으로 잘못된 발췌**입니다.

```go
func generate(out chan<- int) {
    defer close(out)
    for value := 1; value <= 1000; value++ {
        out <- value
    }
}

func firstThree() []int {
    out := make(chan int)
    go generate(out)
    return []int{<-out, <-out, <-out}
}
```

다음을 설명하고 코드를 수정합니다.

1. firstThree가 반환한 뒤 generate는 어느 줄에서 기다릴 수 있나요?
2. 버퍼를 3으로 바꾸면 왜 근본적인 해결이 아닌가요?
3. firstThree에서 out을 닫으면 어떤 패닉이 생길 수 있나요?
4. 생성자에 Context를 전달하면 어느 줄을 select로 바꿔야 하나요?
5. 취소 요청 뒤 실제 종료는 어떻게 확인해야 하나요?

수정한 구조를 제곱 단계까지 확장합니다.
`count=1000, take=0`, `count=1000, take=3`, `count=3, take=3`에서 모두 종료해야 합니다.

정상 출력 예:

```text
앞의 제곱값: [1 4 9]
모든 단계 종료 확인
```

### 힌트

본문의 [pipeline](../../examples/19-channels-select/pipeline/main.go)을 복사해 비교합니다.
취소와 Wait의 순서를 명시한 defer가 필요합니다.
새 단계를 추가할 때는 입력 수신과 출력 전송 양쪽의 취소를 확인합니다.

## 문제 6. 선택 — 신호로 완료 순서 제어하기

**수준: 응용**

개인 폴더: `_practice/19-channels-select/ordered-gates`

```go
func ordered(order []int) (results []int, completed []int, err error)
```

작업 수는 order 길이이며 최대 16개입니다.
order는 0부터 길이-1까지의 인덱스를 정확히 한 번씩 담은 순열이어야 합니다.
작업 index는 결과 칸에 index*10을 씁니다.

각 작업은 자신의 시작 게이트 채널을 기다립니다.
호출자는 order 순서로 게이트를 열고,
해당 작업의 완료를 받은 뒤 다음 게이트를 엽니다.

입력 `[2,0,1]`의 출력:

```text
완료 순서: [2 0 1]
입력 순서 결과: [0 10 20]
```

### 필수 테스트

- 서로 다른 순열 세 개.
- 빈 순열.
- 같은 인덱스를 두 번 사용한 입력.
- 음수와 범위를 벗어난 인덱스.
- 17개 이상 입력.

잘못된 순열을 실행 중 발견하면 영원히 열리지 않는 게이트가 생길 수 있습니다.
따라서 전체 검증을 먼저 끝낸 뒤 고루틴을 시작합니다.

### 힌트

게이트를 닫는 것은 시작 허가입니다.
그 작업이 정말 끝났는지는 별도의 완료값을 받아 확인합니다.
시간 지연이나 고루틴 ID를 순서 제어에 사용하지 않습니다.
