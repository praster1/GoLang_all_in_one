## 문제 1. 실패 메시지와 검사 순서

다음은 테스트의 일부입니다.

```go
got, err := grade(80)
if err != nil {
    t.Errorf("grade(80): %v", err)
}
if got != "우수" {
    t.Errorf("grade(80) = %q; want %q", got, "우수")
}
```

### 확인 질문

1. 첫 Errorf가 실행되면 두 번째 if도 평가되나요?
2. 첫 비교를 Fatalf로 바꾸면 어떤 차이가 생기나요?
3. 필수 준비가 실패하여 got을 안전하게 사용할 수 없다면 어느 쪽이 적절한가요?
4. 실패 메시지에 입력·실제값·기대값을 함께 적는 이유는 무엇인가요?
5. fmt.Println으로 오류를 출력하기만 하면 테스트가 실패하나요?
6. 테스트 함수가 제품 main 함수를 자동으로 실행한다고 가정해도 되나요?

### 오류 상세 정보 사례

아래 코드는 `errors.As`가 실패해도 detail.Input을 읽습니다.
왜 문제가 되는지 설명하고 검사 순서를 고치세요.

```go
var detail *countError
if !errors.As(err, &detail) {
    t.Errorf("unexpected error: %v", err)
}
if detail.Input != "bad" {
    t.Errorf("input = %q", detail.Input)
}
```

### 완료 조건

실패 기록과 현재 테스트 중단을 구분해야 합니다.
두 오류를 한꺼번에 출력하는 것이 항상 좋은 검사는 아님을 설명합니다.
필수 전제가 충족되었을 때만 다음 값에 접근하도록 고칩니다.
오류 상세 정보 검사에서는 원래 테스트가 발견한 오류를 nil 접근 panic으로 가리지 않습니다.

## 문제 3. 범위 안으로 값 보정하기

다음 함수를 구현합니다.

```go
func clamp(value, minimum, maximum int) (int, error)
```

### 함수 계약

- minimum이 maximum보다 크면 errBounds를 반환하고 결과는 0입니다.
- value가 minimum보다 작으면 minimum을 반환합니다.
- value가 maximum보다 크면 maximum을 반환합니다.
- 나머지는 value를 그대로 반환합니다.
- minimum과 maximum이 같은 경우도 유효한 범위입니다.
- 음수 범위를 허용합니다.

`errBounds`는 errors.New로 만든 패키지 수준 sentinel입니다.
테스트는 오류 문자열 전체를 비교하지 않고 `errors.Is`로 원인을 검사합니다.

### 테스트 요구사항

| 사례 | 입력 요약 | 기대 결과 |
| --- | --- | --- |
| 아래 | -1 / 0 / 100 | 0 |
| 최솟값 | 0 / 0 / 100 | 0 |
| 내부 | 50 / 0 / 100 | 50 |
| 최댓값 | 100 / 0 / 100 | 100 |
| 위 | 101 / 0 / 100 | 100 |
| 한 점 | 20 / 7 / 7 | 7 |
| 음수 범위 | -5 / -10 / -2 | -5 |
| 잘못된 범위 | 5 / 10 / 0 | 오류 |

정상 사례는 이름 있는 테이블 테스트로 묶습니다.
잘못된 범위는 오류의 원인과 실패 결과를 검사합니다.
대소 비교로 구현할 수 있으므로 불필요한 뺄셈은 사용하지 않습니다.

main은 clamp(120, 0, 100)을 호출합니다.

```text
보정: 100
```

### 완료 조건

각 사례가 어떤 분기나 경계를 확인하는지 말할 수 있어야 합니다.
min==max를 잘못된 범위로 처리하지 않습니다.
정상 반환의 오류가 nil인지도 확인합니다.

## 문제 4. 순서를 지키는 중복 제거

다음 함수를 구현하고 검사합니다.

```go
func unique(values []string) []string
```

### 함수 계약

- 처음 나타난 문자열만 남깁니다.
- 처음 나타난 순서를 유지합니다.
- 대소문자를 구분합니다.
- 빈 문자열도 하나의 유효한 값입니다.
- nil과 빈 입력 모두 비-nil인 빈 결과 슬라이스를 반환합니다.
- 입력 슬라이스를 수정하지 않습니다.

## 문제 5. 설정값의 기본값과 오류

다음 함수를 작성합니다.

```go
func loadLimit(lookup func(string) (string, bool)) (int, error)
```

조회 키는 `GOLANG_BOOK12_LIMIT`입니다.
lookup이 반환한 bool은 값이 존재하는지를 나타냅니다.

### 입력 계약

- 키가 없으면 기본값 20입니다.
- 키가 있으면 ASCII 숫자로 된 1~100이어야 합니다.
- 앞의 0은 허용합니다.

## 문제 6. 학습자 명단 출력과 쓰기 오류

다음 함수를 구현합니다.

```go
func writeRoster(output io.Writer, names []string) error
```

### 이름 계약

- 이름의 앞뒤 공백을 정리합니다.
- 정리한 결과는 유효한 UTF-8의 1~20룬입니다.
- 정리 후 남은 제어 문자는 허용하지 않습니다.
- 이름의 순서를 유지하며 중복 제거는 하지 않습니다.
- 원본 names를 수정하지 않습니다.

### 출력 계약

민수·지수의 입력은 다음 결과입니다.

```text
학습자: 2
- 민수
- 지수
```

빈 목록은 다음 한 줄입니다.

```text
학습자: 0
```

모든 이름을 검증한 뒤 출력을 시작합니다.
뒤쪽 이름이 잘못되었더라도 표준 출력에 해당하는 Writer는 아직 비어 있어야 합니다.
이름 오류는 errName으로 분류합니다.
쓰기 오류가 발생하면 원인을 `%w`로 감싸 반환합니다.
이미 쓴 바이트는 되돌리지 않습니다.

### 테스트 요구사항

1. bytes.Buffer를 사용하여 헤더·공백·개행까지 비교합니다.
2. 빈 목록을 검사합니다.
3. 정확히 20룬과 21룬을 구분합니다.
4. 빈 이름·중간 줄바꿈·잘못된 UTF-8을 거부합니다.
5. 정상 이름 뒤에 잘못된 이름이 있어도 출력이 비어 있는지 검사합니다.
6. 오류를 반환하는 Writer로 쓰기 실패를 재현합니다.
7. 헤더 쓰기와 이름 쓰기의 실패를 각각 확인합니다.
8. 입력 슬라이스의 공백과 원소 값이 바뀌지 않았는지 검사합니다.

### 완료 조건

검증 실패와 쓰기 실패의 출력 상태를 구분합니다.
검증 실패에는 출력이 없어야 하지만, 쓰기 실패에는 이미 일부 출력이 있을 수 있습니다.
메시지 문자열을 하드코딩하여 원인 비교를 대신하지 않습니다.
외부 파일이나 실제 고장 장치 없이 테스트할 수 있어야 합니다.

<details>
<summary>힌트</summary>

정리한 이름을 새 슬라이스에 모은 뒤 Writer를 사용합니다.
쓰기 가능한 횟수를 제한하는 작은 Writer로 두 번째 Write의 실패도 재현할 수 있습니다.

</details>

## 선택 A. 공개 API의 사용 예를 테스트로 남기기

본문 publicapi 패키지의 공개된 Greeting을 외부 테스트 패키지에서 호출합니다.
다음 두 예제가 각각 무엇을 검증하는지 설명합니다.

- ExampleGreeting: 일반 이름의 인사말.
- ExampleGreeting_empty: 빈 이름의 기본 인사말.

아래 명령으로 예제만 실행합니다.

```sh
go test -v -count=1 -run '^ExampleGreeting' ./examples/12-testing/publicapi
```

### 검토 질문

- Output 주석을 없애면 컴파일과 실행은 각각 어떻게 달라지나요?
- 공개하지 않은 함수를 external test에서 직접 호출할 수 있나요?
- 문자열 앞뒤 공백까지 정확하게 검사해야 한다면 어떤 테스트 방식이 적절한가요?
- 출력 행 순서가 중요할 때 Unordered output을 사용하면 무엇을 놓칠 수 있나요?

실험할 때는 개인 복사본을 사용하고 공식 예제를 의도적인 실패 상태로 남기지 않습니다.
테스트를 위해 불필요한 함수를 공개하는 것으로 문제를 해결하지 마세요.

## 최종 검사

개인 네 구현을 검사할 때는 패키지 경로를 명시합니다.

```sh
go test -count=1 ./_practice/12-testing/clamp ./_practice/12-testing/dedupe ./_practice/12-testing/config ./_practice/12-testing/report
```

저장소 참고 구현은 별도 명령입니다.

```sh
go test -count=1 ./examples/12-testing/... ./solutions/12-testing/...
```

- [ ] 실패할 때 어느 입력이 잘못되었는지 읽을 수 있습니다.
- [ ] 정상값·최솟값·최댓값·오류값을 구분했습니다.
- [ ] 원인 비교 전에 오류가 있는지 확인했습니다.
- [ ] 출력과 원본 보존처럼 반환값 밖의 계약도 검사했습니다.
- [ ] 외부 상태를 테스트 뒤 복원했습니다.
- [ ] 잘못된 구현에서 테스트가 실제로 실패함을 확인했습니다.
